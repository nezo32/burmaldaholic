# Casino buildings v0.2.0 — implementation architecture

Status: **contract for implementation** (2026-10-07, architect B1). Inputs: the research and design in
[docs/design/CASINO_BUILDINGS.md](../design/CASINO_BUILDINGS.md), the root cause in
[docs/review/casino-spawn-root-cause.md](../review/casino-spawn-root-cause.md), the isometric renderer
`docs/design/visual/render_structure.py` and the mockups in `docs/design/visual/mockups/casinos/`.

Owner brief: the casino "looks horrible, just a box"; we want beautiful buildings, our own (no permissively
licensed build exists, design doc §3). **No new games**: every existing game must appear in every full
casino. Casino mode becomes ON by default and the annex chances rise to 0.5 / 0.6 / 0.5 in the v0.1.2 hotfix
(another developer) — this plan **does not touch** `CasinoConfig` defaults, `WorldgenRuntime` chance getters
or casino-mode code. v0.2.0 lanes branch from the hotfix.

The DSL skeleton from §3 is committed with this document and compiles + passes its own checks:
`java/src/main/java/dev/nezo/burmaldaholic/worldgen/logic/blueprint/` and
`java/src/test/java/dev/nezo/burmaldaholic/worldgen/logic/blueprint/BlueprintSkeletonTest.java`.
**Its public signatures are the contract**: lanes may add verbs and parameters (overloads), never rename or
remove one until every lane has merged.

> Gotcha found while prototyping: the repo's `.gitignore` ignores every directory named `build`, so no source
> package may be called `build` (that is why the package is `blueprint`).

## 0. Decisions at a glance

| # | Decision | Why |
|---|---|---|
| D1 | Buildings are generated by a **pure-Java blueprint DSL** on top of the existing `Grid` / `Layout` / `TemplateExporter` | One source of truth with markers / NPC / preset code, deterministic, unit-testable, renders without the game |
| D2 | v0.2.0 templates are **generated at build time** (Gradle task `generateCasinoPack` → `build/generated/casino-pack`), not committed. The v0.1 templates stay committed and **frozen** byte-for-byte | No binary merge conflicts between 5 lanes; v0.1 saves keep loading their pieces |
| D3 | **No processor lists** (26.2 vs 26.3 changed the processor-list JSON). Variety = pool alternatives + per-style palettes; randomness at placement = the existing code-side markers (loot chests) with the chunk's `RandomSource` | Works on both supported versions without per-version JSON |
| D4 | Standalone casino = **one structure per style** (`burmaldaholic:casino_tudor`, `_oasis`, `_safari`, `_alpine`, `_ice_palace`) of our own structure type `burmaldaholic:casino` (wraps vanilla jigsaw + gate + flatness + completeness), all in one `structure_set` `burmaldaholic:casinos` (spacing 40, separation 12), tagged `#burmaldaholic:casino` for `/locate` | Vanilla village pattern; per-style biome tags; one id family for `/locate` and explorer maps |
| D5 | A casino is **complete or absent**: the structure type rejects a start whose jigsaw assembly lacks the entrance, floor or bar piece | "Every game in every full casino" can then be proven statically |
| D6 | Multi-piece casinos register as **one** casino: a `StructureStart` placement context gives every marker the same casino id and the union box of the start's casino pieces | Table presets, NPC respawn, attract FX keep working across pieces |
| D7 | Annexes (village "Lucky Villager", Piglin Parlor, High Roller Lounge) stay **single templates** placed by the existing mixins, rebuilt with the DSL under **new ids**; the hotfix chances apply | Their hosts decide placement; no jigsaw needed; old ids frozen for old saves |
| D8 | **No entities and no signs in templates** (item frames, maps, paintings, sign text). Signage = pixel letters + froglight bulbs + banners | Entity / sign-text NBT drifts between versions and cannot be rotated safely by us; map art needs per-world map ids |
| D9 | Reviews happen on **renders + in-game photos** produced by tools, attached to every PR that changes a piece | The "box" shipped because nobody looked at it |

## 1. Constraints recap

- Java 26.2 + 26.3 from one jar. Templates are written with `DataVersion 4903` (26.2) — newer versions upgrade
  them through DFU. Never write a newer DataVersion.
- Structure JSON fields used must exist in **both** versions; every generated JSON is loaded by a GameTest on
  both (`build` and `build -Pmc=26.3` run `runGameTest`). Allowed jigsaw fields (verified in 26.2 sources):
  `start_pool, size, start_height, use_expansion_hack, project_start_to_heightmap, max_distance_from_center`
  (+ the settings `biomes, spawn_overrides, step, terrain_adaptation`). Do **not** use `pool_aliases`,
  `dimension_padding`, `liquid_settings`, `start_jigsaw_name` (not needed, less to break).
- `"processors": "minecraft:empty"` is the only processor value we write (D3).
- `Structure.generate` gained a parameter in 26.3: our code never calls it directly — building by command goes
  through the vanilla command dispatcher (`place structure …`), see §6.5.
- Saved worlds from v0.1.x reference `burmaldaholic:worldgen/village_casino_<style>`, `…/piglin_parlor`,
  `…/high_roller_lounge` templates and pools, and `CasinoIndex` records carry those layout ids. **These ids, their
  sizes and bytes never change** (`TemplateExportTest` keeps guarding them). New buildings get new ids under
  `worldgen/casino/…`.
- Casino mode gate: the standalone structure is gated by `WorldgenRuntime.active()` exactly like the annexes
  (mode is ON by default after the hotfix).

## 3. The blueprint DSL (pure Java)

### 3.1 Frame and conventions

- Template-local coordinates, inclusive boxes, y = 0 is the lowest template row.
- **FRONT = +z (south)** for every piece — the same as all v0.1 layouts. A viewer outside the front looks
  north; their left is −x. Pixel text reads with x increasing.
- Non-start pieces are authored with their **entry connector on their own +z face** (pointing south); the
  jigsaw rotates them into place. So every piece is designed "door at the bottom of the plan".
- The **floor row** is the first air row above the floor blocks; kits, games and NPC markers take the floor
  row as their `y`.
- Cells never written are `null` = structure void (terrain kept). A piece clears what it occupies
  (`room()` clears the inside) and should clear the air above its roof line to its top row only where the
  silhouette needs it (trees cut cleanly, nothing else).
- Later verbs overwrite earlier ones. Canonical order: `foundation → room → frame → windows → door → floors /
  carpets → kits → lights → roof → facade/marquee → markers → jigsaws`.

### 3.2 Palette roles

`Role` (committed): `FOUNDATION, FLOOR, FLOOR_ACCENT, CARPET, CARPET_ACCENT, WALL, WALL_BASE, FRAME, BEAM,
CEILING, ROOF, ROOF_TRIM, TRIM, GLASS, PANE, LIGHT, LIGHT_HANGING, NEON_A, NEON_B, SIGN_BACK, BULB, ACCENT,
COUNTER, STOOL, PLANTER, PATH`. A `Material(full, stairs, slab)` resolves shaped forms; a `Palette` must map
every role (`Palette.check()` throws at generation time). Pieces call `b.set(x, y, z, Role.WALL)`; literal
block ids are allowed only for role-independent decor (iron bars, chains, brewing stands, flower pots, candles).

### 3.3 Verbs (committed skeleton + planned additions)

| Verb | Status | Notes |
|---|---|---|
| `Blueprint.of(id, kind, sx, sy, sz, palette)` | committed | `id` = layout id, e.g. `casino/tudor/floor_a` → template `burmaldaholic:worldgen/casino/tudor/floor_a` |
| `set / fill / clear` (block or role) | committed | bounds-checked (throws) |
| `foundation(x0, z0, x1, z1, topY)` | committed | solid skirt y 0..topY |
| `room(box)` → `Room` with `.frame(every) .windows(side, every, sill, h) .door(side, center, w, h) .done()` | committed | room inside registered as *interior* for the light check |
| `hipRoof(x0, z0, x1, z1, baseY, layers)` | committed | stairs rings + cap |
| `marquee(word, centerX, topY, z)` | committed (front only) | NEON_A/NEON_B alternating letters on SIGN_BACK, BULB border every 2 |
| `game(Game, x, y, z, playerSide)` | committed | writes `facing=playerSide`, records a `GameSpot` |
| `keepClear(box)` | committed | must stay air/carpet; checked |
| `npc(role, x, y, z, facing)`, `chest(table, …)`, `anchor(…)`, `marker(…)` | committed | v0.1 marker format unchanged |
| `jigsaw(x, y, z, out, name, target, pool, finalState)` | committed | `rigid` joint, orientation `<out>_up` |
| `kit(kit, x, y, z, front)` | committed | |
| `setNbt(x, y, z, block, nbt)` | CB-2 | per-block NBT (banners only in v0.2.0); needs the additive `Layout` field |
| `banner(x, y, z, facing, base, patterns…)` | CB-2 | wall banner + pattern NBT (`{pattern: "minecraft:rhombus", color: "red"}` list, 26.2 format, DFU upgrades) |
| `inlay(pattern, x, y, z)` | CB-2 | pixel suit symbols ♠♥♦♣ (5×5) in floor / carpet |
| `marquee(word, side, …)`, `bladeSign(word, …)` (vertical) | CB-3 (`Facades`) | |
| `gableRoof, dome, steppedParapet, thatch, mansard` | CB-3 (`Roofs`) | |
| `clerestory(box)` | CB-2 | raised glass band over the gaming floor |

### 3.4 Kits (furniture prefabs)

`Kit` = `(Blueprint b, x, y, z, Facing front) -> void`; a kit only uses public verbs. Committed: `tablePod(game,
dealerRole)`, `slotBank(slots, count)`, `cashierCage(cashier)`, `chandelier(drop)`. CB-2 adds: `bar(length)`
(counter of COUNTER stairs, brewing stands/flower pots/candles as bottles, barrels, stools), `vipSofa`
(stairs + wool cushions), `planter`, `ropeBarrier` (fence posts + chain), `duelPit`
(5×5 clear sunken ring for Dice Duel / Coin Flip throws, `DuelStage` throws dice to the ground between players),
`lampPost`, `portico(columns)`, `machineAlcove(game)` (wheel / plinko niche with neon frame), `chipStacks`
(decor from our own blocks if any exist; else candles + gold pressure plates).

Kit footprint rules (enforced by `Checks`):
1. A game block stands on a solid floor block (no floating tables).
2. The **player cell** in front of every game block (its `facing` side) is air or carpet.
3. Above every table a **3×3×3 keep-clear volume** (`Kits.BOARD_CLEARANCE`) for the in-world board renderer;
   the in-world-board lane must keep its render bounds inside that volume (coordinate before changing it).
4. Block light ≥ 10 directly above every game block; every interior air cell over a solid floor has light ≥ 1
   (mobs spawn at block light 0). `Checks.light` is a flood-fill approximation; the GameTest measures real light.
5. Stools are decor beside the player row, never on it. Dealer NPCs stand on the opposite side.
6. Min 2 free blocks of aisle around every pod (checked by `Checks` once CB-2 adds `aisle` boxes).

### 3.5 Game blocks, facing and block entities

- All game blocks are single blocks with one property `facing` (`CasinoTableBlock`, horizontal, "faces the
  placer" = **the side players stand on**). The DSL writes `facing=playerSide`; vanilla rotates it with the piece
  (`CasinoTableBlock.rotate`). Tests assert it after placement in all four rotations.
- **No block-entity NBT for game blocks**: the block entity is created fresh on placement; stakes / presets
  come from the casino record at runtime (`WorldgenPresets`), bots from `botDefaults`. This also means a
  template survives game-module changes.
- If a game module is absent, its block id loads as air (v0.1 behaviour) — `Checks` still requires it.
- `Game` enum (committed) lists every block id incl. tiers/variants and groups them into `Family`.
  `Family.REQUIRED` = all ten families: CASHIER, BLACKJACK, ROULETTE, CRAPS, BACCARAT, UTH, POKER, SLOTS,
  WHEEL, PLINKO. Scratch cards are sold by the Croupier at the cashier (existing `NpcShop`), Coin Flip /
  Dice Duel are item games played anywhere — the `duelPit` kit gives them a stage.
- NPCs: Croupier (cashier), Loan Shark (bar booth), Baccarat Dealer (behind the baccarat table), Piglin Dealer /
  Piglin Moneylender (Parlor), Shulker Croupier (Lounge). No new NPC roles. Other tables get a dealer
  *station* (decor: lectern facing the table + candles) — no entity.
- Loot: `chest(CasinoLoot.Table, …)` markers only (code-filled with the chunk RNG, deterministic per seed).

### 3.6 Determinism

The DSL has no randomness. A generator that wants variation takes a `long variantSeed` constant and uses
`new SplittableRandom(seed)` in a fixed draw order — output is fixed per build. World variety comes from
pool alternatives (`floor_a` / `floor_b`, `office` / `vip`), the five styles, and placement RNG for loot.
`PackGen` output must be byte-identical across runs and JVMs (`PackFilesTest.deterministic` exports twice and
compares; `Map`s used for output are `LinkedHashMap` / `TreeMap`).

### 3.7 Build-time generation (D2)

```groovy
// java/build.gradle (CB-1)
def casinoPackDir = layout.buildDirectory.dir("generated/casino-pack")
def generateCasinoPack = tasks.register("generateCasinoPack", JavaExec) {
    dependsOn tasks.named("compileJava")
    // NOT runtimeClasspath: it contains processResources output → circular dependency
    classpath = sourceSets.main.output.classesDirs + sourceSets.main.compileClasspath
    mainClass = "dev.nezo.burmaldaholic.worldgen.logic.PackGen"
    args casinoPackDir.get().asFile.absolutePath
    inputs.files(sourceSets.main.output.classesDirs)
    outputs.dir(casinoPackDir)
}
sourceSets.main.resources.srcDir(files(casinoPackDir).builtBy(generateCasinoPack))
```

`PackGen` writes `resourcepacks/casinos/data/burmaldaholic/…` (templates, pools, structures, set, tags) and
`previews/manifest.json` (every piece and every assembly with offsets / rotations for the renderer, §8).
The legacy v0.1 files remain in `src/main/resources/resourcepacks/casinos/` (committed, frozen); the two trees
never contain the same path (`PackFilesTest` asserts it). The jar, `runGameTest`, `runClientGameTest` and
`runClient` all see the merged pack through `processResources`.

Fallback if Loom misbehaves with the generated srcDir: commit the generated files like v0.1
(`BURMALDAHOLIC_EXPORT_STRUCTURES=1`), with the rule that **only the integrator** regenerates after each merge.

## 4. Pieces and variants

### 4.1 Overworld standalone casino (5 styles × pieces)

Pool and piece ids per style `<s>` ∈ `tudor, oasis, safari, alpine, ice_palace`:

| Piece (layout id `casino/<s>/…`) | Size X×Y×Z | Pool `burmaldaholic:worldgen/casino/<s>/…` (weight) | Required games inside | Connectors |
|---|---|---|---|---|
| `entrance` (start) | 31×18×11 | `entrance` (1) | CASHIER (+Croupier), WHEEL, PLINKO | back → `floor` |
| `floor_a` / `floor_b` | 31×14×17 | `floor` (1 / 1) | BLACKJACK, ROULETTE, CRAPS, BACCARAT (+Baccarat Dealer), UTH, POKER, SLOTS copper ×6 + gold ×4 | front ← entrance; east → `bar`; back → `rear` |
| `bar` | 13×11×17 | `bar` (1) | — (gold slots ×3, Loan Shark, duel pit) | west ← floor |
| `office` | 15×9×9 | `rear` (2) | — (loot chest) | front ← floor |
| `vip` | 17×12×13 | `rear` (1) | — (netherite slots ×2, player-banked baccarat, player-banked UTH, poker #2) | front ← floor |

`floor_a` and `floor_b` hold the same games in different compositions (a: two rows of pods + centre aisle;
b: an oval "pit" with tables around a sunken centre). Required families live in `entrance + floor`, and the
structure type rejects assemblies without `entrance + floor + bar` (D5). `AssemblyTest` enumerates every
combination (2 floors × 2 rears = 4 per style) and asserts `Checks.families(...) ⊇ Family.REQUIRED`, no piece
overlap, jigsaw pairs consistent, and footprint ≤ 47×47.

Jigsaw names (`burmaldaholic:casino/<connector>`): `entrance_back`↔`floor_front`, `floor_side`↔`bar_side`,
`floor_back`↔`rear_front`. Parent connector's `target` = child connector's `name`; `pool` on the parent
names the child pool; children's own entry connectors use `pool: minecraft:empty`. `finalState` = the FLOOR
block (connectors sit in the floor row of the doorway). Doorways are 3 wide × 3 high, opened by both pieces.

Structure JSON per style (`data/burmaldaholic/worldgen/structure/casino_<s>.json`, written by `PackFiles`):

```json
{
  "type": "burmaldaholic:casino",
  "biomes": "#burmaldaholic:has_structure/casino_<s>",
  "step": "surface_structures",
  "spawn_overrides": {},
  "terrain_adaptation": "beard_thin",
  "start_pool": "burmaldaholic:worldgen/casino/<s>/entrance",
  "size": 3,
  "start_height": { "absolute": -3 },
  "project_start_to_heightmap": "WORLD_SURFACE_WG",
  "max_distance_from_center": 48,
  "use_expansion_hack": false,
  "max_height_range": 6,
  "required_pieces": ["entrance", "floor", "bar"]
}
```

`start_height -3` + 3-row foundation puts the floor block at ground level (the template's foundation rows
y 0..2 sink into the terrain; `beard_thin` fills gaps under the rest). Every piece shares the same floor row.

`structure_set` `data/burmaldaholic/worldgen/structure_set/casinos.json`:

```json
{
  "structures": [ { "structure": "burmaldaholic:casino_tudor", "weight": 1 }, … five entries … ],
  "placement": {
    "type": "minecraft:random_spread", "spacing": 40, "separation": 12, "salt": 1592770897,
    "exclusion_zone": { "other_set": "minecraft:villages", "chunk_count": 3 }
  }
}
```

Biome tags (`data/burmaldaholic/tags/worldgen/biome/has_structure/casino_<s>.json`), referencing vanilla tags so
26.x biome changes follow automatically, `"required": false` for single biomes:

| Style | Look | Biomes |
|---|---|---|
| tudor | Tudor gambling hall | `#minecraft:has_structure/village_plains`, meadow, forest, birch_forest, flower_forest |
| oasis | Art-deco oasis | `#minecraft:has_structure/village_desert`, badlands, wooded_badlands |
| safari | Safari lodge | `#minecraft:has_structure/village_savanna`, savanna_plateau |
| alpine | Alpine lodge | `#minecraft:has_structure/village_taiga`, cherry_grove, old_growth_spruce_taiga |
| ice_palace | Ice palace | `#minecraft:has_structure/village_snowy`, snowy_taiga, ice_spikes |

Overlapping tags are harmless: the set tries the structures in weighted-shuffled order and the first whose
biome matches wins (vanilla `ChunkGenerator.tryGenerateStructure`). Structure tag
`data/burmaldaholic/tags/worldgen/structure/casino.json` lists all five → `/locate structure #burmaldaholic:casino`.

### 4.2 Village annex "Lucky Villager" v2 (CB-3)

Single template per `VillageStyle`, id `casino/annex/<style>`, footprint **≤ 17×17** (the street-end fit of
v0.1 was 89 % at 17×17 — do not grow it), height ≤ 15 (taller facade with the marquee, mezzanine-free).
Placed by the existing `VillageCasinos` (CB-1 swaps `Layouts.village(style)` for
`CasinoPack.villageAnnex(style)`, legacy layout kept for old saves). It is a full casino too (§7.4 plan).
Palettes = the Overworld style mapped from the village type (plains→tudor, desert→oasis, savanna→safari,
taiga→alpine, snowy→ice_palace).

### 4.3 Piglin Parlor v2 (CB-4)

Single template `casino/parlor`, **33×16×33**, placed by `CasinoStructures.appendParlor` (unchanged logic;
CB-1 swaps the layout). Rows 13..15 stay structure void (Nether rock above is kept). The survey must show fit
≥ 90 % of bastions (v0.1: 30/30 at 21×21).

### 4.4 High Roller Lounge v2 (CB-4)

Single template `casino/lounge`, **25×14×25**, on the highest End City tower top (unchanged logic). Cantilevered
penthouse: the floor overhangs the tower top, purpur struts under the overhang. Fit ≥ 90 % (v0.1: 117/117 at
15×15); if not, shrink to 23×23.

### 4.5 Coexistence

- Standalone casinos never land within 3 chunks of a village placement (exclusion zone); the village annex is
  max 1 per village (existing). A world therefore has: standalone casinos every ~830 blocks, plus annexes in
  ~50 % of villages (hotfix chance), Parlors in ~60 % of bastions, Lounges in ~50 % of End Cities.
- `CasinoKind.CASINO` (new, "Grand Casino" / "Казино") for the standalone structure; annexes keep their kinds.
  Table presets: CASINO → defaults (no special stakes); VIP tables use the High-Roller variants only through
  their own block ids (`*_high_roller`), so no preset change is needed.
- Max one casino record per StructureStart (D6).

## 6. Runtime integration (CB-1)

### 6.1 Structure type `burmaldaholic:casino`

```java
public final class CasinoStructure extends Structure {
    public static final MapCodec<CasinoStructure> CODEC = RecordCodecBuilder.mapCodec(i -> i.group(
            JigsawStructure.CODEC.forGetter(s -> s.jigsaw),                // inlines all vanilla jigsaw fields
            Codec.intRange(0, 64).optionalFieldOf("max_height_range", 6).forGetter(s -> s.maxHeightRange),
            Codec.STRING.listOf().optionalFieldOf("required_pieces", List.of()).forGetter(s -> s.required))
        .apply(i, CasinoStructure::new));
    // super(new StructureSettings(jigsaw.biomes(), jigsaw.spawnOverrides(), jigsaw.step(), jigsaw.terrainAdaptation()))
    protected Optional<GenerationStub> findGenerationPoint(GenerationContext ctx) {
        if (!WorldgenRuntime.active()) return Optional.empty();
        if (!flatEnough(ctx) || flooded(ctx)) return Optional.empty();       // 5 heightmap samples: centre ± 20
        Optional<GenerationStub> stub = jigsaw.findValidGenerationPoint(ctx); // public; also checks the biome
        if (stub.isEmpty()) return stub;
        StructurePiecesBuilder built = stub.get().getPiecesBuilder();         // runs the jigsaw ONCE
        if (!hasRequired(built)) return Optional.empty();                     // D5
        return Optional.of(new GenerationStub(stub.get().position(), Either.right(built))); // never re-run it
    }
}
```

Never call `getPiecesBuilder()` twice on the vanilla stub: the jigsaw assembles **inside** that consumer with
the context's random, so a second call gives a different layout. The `Either.right(built)` re-wrap is required.
`flooded`: `WORLD_SURFACE_WG − OCEAN_FLOOR_WG > 0` at any sample → water → reject. `hasRequired`: the
`PoolElementStructurePiece` templates, mapped with `CasinoElements.layoutOf`, contain an id ending in each
required name. If the codec composition fails on 26.3, fall back to plain `minecraft:jigsaw` + gating in a
`ChunkGenerator.tryGenerateStructure` mixin; the survey numbers then decide whether flatness is needed.

### 6.2 Gate and chances

The standalone structure has no chance knob (the spread *is* the rate). The hotfix's chances apply to annexes
only. A config switch `worldgen.casino.enabled` (default true) is checked in `findGenerationPoint` — CB-1 adds
it to the worldgen config section (coordinate with whoever owns `CasinoConfig` after the hotfix).

### 6.3 One casino per StructureStart (D6)

`StructureStartMixin` wraps `StructureStart.placeInChunk`: before the piece loop it computes, from
`pieceContainer.pieces()`, the casino pieces (`CasinoElements.layoutOf`), and stores
`CasinoPlacement.Context(casinoId = CasinoRecord.idFor(dim, first casino piece origin), box = union of their
bounding boxes, kind)` in a ThreadLocal; cleared in `finally`. `CasinoMarkers.handle` uses the context when
present (all pieces → same id, the anchor registers the union box); without one (v0.1 `CasinoBuilder` single
place, legacy) it keeps today's per-piece behaviour. Every chunk computes the same context from the same saved
pieces, so ids are stable across chunks and restarts.

### 6.4 Markers

Unchanged format. The anchor marker lives only in the start piece (`entrance`, annex, parlor, lounge).
`Markers.parse` accepts every id `Layouts.byId` knows (v0.2 ids included through §5).

### 6.5 Commands, `/locate`, building by hand

- `/locate structure #burmaldaholic:casino` and `/locate structure burmaldaholic:casino_tudor` work through the
  tag/ids. The CB-1 op command `/casino worldgen locate` was dropped when v0.1.3 merged in: the every-player
  `/casino locate` (`CasinoLocator`, docs/handoff/v013-locate.md) covers all v0.2 casinos — the standalone set
  `burmaldaholic:casinos` is one more host grid (structures of `#burmaldaholic:casino`, no hash gate,
  `LocateRules.CAP_CASINO_CHUNKS`), annexes / Parlor v2 / Lounge v2 ride on the v0.1 hosts and gates, and every hit
  is confirmed in the real structure start (`CasinoPlacement.of`: kind + union box of the start's casino pieces).
- `/casino worldgen build casino [style]` dispatches `place structure burmaldaholic:casino_<style> <pos>`
  through `server.getCommands()` (version-proof; `/place structure` ignores biomes and runs the same
  `placeInChunk` path, so markers + D6 behave as in worldgen). Annex kinds keep `CasinoBuilder.build`.
- Explorer map trade from the Croupier: **out of scope** for v0.2.0 (new functionality); the tag makes it a
  one-liner later.

## 7. Visual quality bar

A piece is not done until its renders (§8) pass the review checklist (§7.6). Measurable bar for every full casino:

- **Silhouette**: at least 3 height levels (forecourt/portico ≤ 6, hall 10–14, roof feature / tower / dome ≥ 15
  above the floor). No flat box: a flat roof must have a stepped parapet + roof feature.
- **Facade**: symmetric front, 5-wide entrance with portico or canopy, marquee ≥ 18 wide × 7 tall lit with
  froglight bulbs every 2 blocks, two lamp posts on a 31×5 forecourt path. Readable at night from 100 blocks
  (CasinoPhoto night shot: the letters must be distinguishable).
- **Walls**: never a single material plane > 6×4 blocks — break with FRAME pilasters (every 5–6), WALL_BASE
  plinth row, window rhythm, TRIM band under the eaves.
- **Interior**: one straight carpet runner from the door to the cashier and on to the rear arch; tables in pods
  with stools, rope barriers and dealer stations; slot banks against walls under a neon strip; at least one
  floor inlay (suits), chandeliers on a 6-grid, planters at corners, light ≥ 10 over tables, ceiling ≥ 5 high
  over the gaming floor (clerestory 7–8).
- **Every game** (all ten families) reachable on foot from the door, each game block with a free player cell.
- **Lighting palette**: froglights / sea lanterns / lanterns / end rods / shroomlight only; no redstone lamps
  (unpowered after placement), no torches inside (they read as "dungeon").
- **Signage**: pixel letters (concrete NEON_A/NEON_B) + bulbs; wall banners flanking the door with suit-like
  patterns in style colours (`rhombus` ≈ ♦, `flower` ≈ ♣, `circle`; `skull` for the Parlor); floor inlays.
  No sign blocks, no item frames, no maps (D8).

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `CasinoStructure` codec composition (`JigsawStructure.CODEC` inlined) breaks on 26.3 or fails `verifyRange` | GameTest `casinoRegistryLoads` on both versions in CB-1 PR-1; fallback: plain `minecraft:jigsaw` + gate in a `tryGenerateStructure` mixin (§6.1) |
| Jigsaw re-run gives a different layout (the stub consumer) | Re-wrap with `Either.right(built)` (§6.1); test: same seed → same piece list twice |
| Big rigid pieces on hills → floating / buried | `max_height_range` flatness pre-check, 3-row foundation skirt, `beard_thin`; terrain test §9.4 |
| Bigger annexes fit less often (Parlor 33², Lounge 25²) | Survey fit ≥ 90 % before merge, shrink if not |
| Block id typos / missing module → silent air | `templatePalettesResolve` GameTest, magenta in renders, `Checks` on games |
| v0.1 saves break when templates change | Old ids frozen byte-for-byte (`TemplateExportTest`); new ids for all v2 content |
| Loom + generated resources srcDir (circular task deps, IDE) | classpath without resources (§3.7); fallback to committed files with an integrator regenerating |
| In-world board renderer grows beyond the 3×3×3 clearance | `Kits.BOARD_CLEARANCE` is the shared constant; in-world-board lane changes it only with a `PieceChecksTest` run |
| Gaming floor too bright/dark, mobs spawning | `Checks.light` + real-light GameTest |
| Too many NPCs / BEs → lag on servers | Content budget asserted in `AssemblyTest`; idle tick budget test |
| Lanes edit the same file | Ownership map §2; pre-wired registries (`CasinoPack` → three per-lane lists, `OverworldStyles` owned by CB-3, gametest `fabric.mod.json` by CB-5) |
| `.gitignore` ignores directories named `build` | Package is `blueprint`; never name a source dir `build` |
