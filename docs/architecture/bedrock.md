# Burmaldaholic: Bedrock Edition architecture

Owner: R2 (researcher + architect). Code: `bedrock/`. Researched 2026-09-23.

## 1. Versions: what "26.2–26.3" means on Bedrock

Since 2026 Mojang numbers both editions by year, but each edition counts its drops differently.
Java uses `26.<drop>`. Bedrock uses `26.<drop*10>` in marketing and **`1.26.<n>` internally**:
manifests, npm packages and `min_engine_version` all use the internal number.

| Java drop | Released | Bedrock release (same drop) | internal | `@minecraft/server` | `@minecraft/server-ui` |
|---|---|---|---|---|---|
| 26.2 "Chaos Cubed" | 2026-06-16 | Bedrock 26.30 | 1.26.30 | **2.8.0** | **2.1.0** |
| (between drops) | 2026-08-04 | Bedrock 26.40 | 1.26.40 | 2.9.0 | 2.1.0 |
| 26.3 "Wilderness Bound" | 2026-09-15 | Bedrock 26.50 | 1.26.50 | 2.10.0 | 2.2.0 |
| next (preview) | – | 26.60 preview | 1.26.60 | 2.11.0-rc / 2.12.0-beta | 2.3.0-rc / 2.4.0-beta |

The dates come from npm publish times of `@minecraft/vanilla-data` and `@minecraft/server`, the
Minecraft Wiki, and minecraft.net.

**Decision:**
- Target the whole 26.2–26.3 window: `min_engine_version` is `"1.26.30"`, and the manifest
  depends on `@minecraft/server` **2.8.0** and `@minecraft/server-ui` **2.1.0**. These are the
  stable modules that shipped with 1.26.30. Newer clients (1.26.40, 1.26.50 and later) keep
  loading older stable module versions.
- The npm devDependencies are pinned to exactly those versions, so TypeScript rejects any API
  added in 2.9 or later. `scripts/build.mjs` fails if `pack.json` and `package.json` disagree.
- **Stable only.** The pack does not depend on `-beta` modules or on any experiment toggle.
  To move up later (for example to 2.10.0 with min engine 1.26.50), change `pack.json`,
  `scriptModules` and the devDependencies together.

All of this lives in `bedrock/pack.json`, which also holds the fixed UUIDs, the languages and
the manifest format.

## 2. Pack format

- **Manifest `format_version: 3`**, generated by the build (never hand-written). All versions
  are semver strings, and `metadata.authors` is required. Version 3 is needed for **pack
  settings** (see §4).
  - Fallback: set `"manifestFormat": 2` in `pack.json`. The build then emits a v2 manifest with
    array versions and no pack settings.
- **BP modules:** `data` plus `script` (`language: javascript`, `entry: scripts/main.js`).
- **BP dependencies:** the RP header UUID, `@minecraft/server` 2.8.0 and `@minecraft/server-ui`
  2.1.0.
- **RP:** one `resources` module, `pack_scope: "world"`, and a dependency back on the BP.
  Apply one and you get both.
- **Fixed UUIDs** (never change them, or existing worlds lose the pack):

  | Role | UUID |
  |---|---|
  | BP header | `4ecd403b-ec26-42d3-bb5d-c937ffe9b66e` |
  | BP data | `62f82d44-97a6-44d6-9878-d017d0ff35b0` |
  | BP script | `91485050-d4db-421d-8efb-d4b268a5071d` |
  | RP header | `cd52e210-ac4c-488d-abc3-805d6ed0ffaf` |
  | RP resources | `04c469b4-eed3-494e-90e4-98d8bc930054` |

- **Pack version:** taken from `MOD_VERSION` (release CI), otherwise from `package.json`
  `version`. Only `X.Y.Z` is used; any pre-release suffix is dropped.
  - Note for `docs/ci.md`: with manifest v3 the version is written as a semver *string*, not an
    array. The manifestFormat 2 fallback writes arrays.
- **Texts:** both `BP/texts/` and `RP/texts/` get `languages.json` (`["en_US","ru_RU"]`),
  `language_names.json`, and the merged `en_US.lang` / `ru_RU.lang`.
  - rawtext is translated on the client from RP texts.
  - The BP copy is needed for the manifest `pack.name` / `pack.description` and the pack-settings
    labels.
- **Output:** `dist/Burmaldaholic.mcaddon`, a zip holding `Burmaldaholic_BP/` and
  `Burmaldaholic_RP/`. The unzipped packs stay in `build/BP` and `build/RP`.

### Data-driven JSON versions (guidance)

Every `format_version` must be **≤ 1.26.30** (the min engine). Stricter component validation
applies from 1.26.50 formats, so do not use them yet.

| File | Folder | Suggested `format_version` |
|---|---|---|
| Items | `BP/items/<module>/` | `1.26.30`. Use `minecraft:display_name` with a lang key such as `item.burmaldaholic:chip_100`, plus `minecraft:icon` and `minecraft:custom_components`. |
| Blocks | `BP/blocks/<module>/` | `1.26.30`. Custom components v2 (`minecraft:custom_components` with params) are registered in script via `event.blockComponentRegistry` during `onStartup`. |
| Entities (server) | `BP/entities/<module>/` | `1.26.30` |
| Client entities | `RP/entity/<module>/` | `1.10.0`. Render controllers and animations `1.10.0`, geometry `1.16.0`. |
| Feature / feature rules | `BP/features`, `BP/feature_rules` | `1.21.x`–`1.26.30` |
| Jigsaw worldgen | `BP/worldgen/{structures,template_pools,processors,structure_sets}` plus `.mcstructure` files in `BP/structures/` | Must be ≤ 1.26.30. **Verify in game.** |

Always check the Content Log (Settings → Creator → Content Log GUI) after adding JSON.

## 3. Script API surface we use (all stable in 2.8.0 / 2.1.0)

| Need | API |
|---|---|
| Lifecycle | `system.beforeEvents.startup` (early execution: register commands and custom components), then `world.afterEvents.worldLoad` |
| Slash commands | **`CustomCommandRegistry`** (stable since `@minecraft/server` 2.0) via `StartupEvent.customCommandRegistry`. Names need a namespace (`/burmaldaholic:casino`). Set `cheatsRequired: false`. Permission levels: `Any` / `GameDirectors` / `Admin` / `Host` / `Owner`. The callback runs in restricted mode, so defer the real work with `system.run` (core does this for you). The `description` is a plain string and the engine does not translate it. |
| Forms | `ActionFormData` (menus: `title` / `body` / `button` / `label` / `header` / `divider`), `ModalFormData` (`toggle` / `slider` / `dropdown` / `textField` / `submitButton`), `MessageFormData` (yes/no). Every text argument accepts **RawMessage**. |
| Live-updating UI | **`CustomForm` / `MessageBox` with `Observable*`** (data-driven UI, stable in server-ui 2.1.0). Bind an `ObservableString` or `ObservableUIRawMessage` and the open form updates in place. Good for slot reels or a roulette ball. Everything else stays on the classic forms. |
| Text | RawMessage `{translate, with: {rawtext:[...]}}`, which allows nested translated args. Build it with `t()`, `plural()`, `join()` and `lit()` from core. |
| HUD | `player.onScreenDisplay.setActionBar` (one line, fades after about 3 s), `setTitle` (with `subtitle` and fade times), `updateSubtitle`. Scoreboard sidebar via `world.scoreboard.setObjectiveAtDisplaySlot`. |
| Persistence | `world` / `entity` dynamic properties (`boolean \| number \| string \| Vector3`; store JSON strings for structs) and scoreboards. |
| Interactions | `world.afterEvents.playerInteractWithEntity` (dealer NPCs), `playerInteractWithBlock`, block `onPlayerInteract` custom components (tables and machines), item `onUse`. |
| Structures | `world.structureManager.place(...)` (script fallback for worldgen). |
| Pack settings | **`world.getPackSettings()`**, stable since 2.8.0. It is not in 2.7.0. |

**Beta-only, so do NOT use** (checked against the 2.8.0 typings):
- `world.beforeEvents.chatSend` and `afterEvents.chatSend`. Chat-typed bets are impossible; use
  forms or commands.
- Anything else that is missing from `node_modules/@minecraft/server/index.d.ts`. Since
  `tsc --noEmit` runs against the stable 2.8.0 typings, lint rejects beta calls automatically.

If a feature truly needs a beta API, propose it in review with a stable fallback. Do not ship it
behind an experiment toggle.

## 4. "Casino mode on at world creation"

Bedrock add-ons cannot add fields to the vanilla Create World screen. We combine three layers,
resolved by `resolveCasinoEnabled` in `core/logic/mode.ts` (first defined value wins):

1. **World override.** Operators run `/burmaldaholic:casino` to open an admin `ActionFormData`, which can
   toggle casino mode. The choice is saved in the world dynamic property `burmaldaholic:casino_mode`.
   The same form edits each module's declared config.
   - It can also be set with `/scriptevent burmaldaholic:admin casino_mode true|false` (already
     implemented in `core/module-core.ts`).
   - GAME_DESIGN §2 also asks for a **first-op Setup form** on first world load. It writes this
     same property and is B-core's job (wave 2). It layers on top of this resolution without
     changing it.
2. **Pack setting.** The manifest v3 `settings` holds a toggle `burmaldaholic:casino_mode` (default
   on), with labels given as lang keys.
   - Players see it through the gear or settings button on the pack when they apply it at world
     creation, and later under World settings → Behavior packs.
   - Script reads it with `world.getPackSettings()`.
   - Microsoft's doc page still calls BP pack settings "experimental", but the API is in the
     stable 2.8.0 module. If the settings UI does not appear, the value is simply absent and
     layer 3 applies (safe degradation). **Manual test item.**
3. **Default `true`.** Activating the add-on on a world at creation is itself the switch. A
   world without the add-on is a vanilla world.

Every gameplay entry point must check **`isCasinoEnabled()`**:
- `ctx.guard(fn)` wraps event handlers.
- `registerCommand` checks it automatically, unless `bypassCasinoGuard` is set (admin only).

```
  modules.json         module id -> src folder (pre-populated, never edited by feature devs)
  assets/pack_icon.png
  src/
    main.ts            entry -> bootstrap(MODULES)

    core/              economy, config, casino guard, HUD, commands, admin form, registry
      index.ts         the only core entry for modules (plus core/logic/**)
      logic/           PURE: ids, plural, rawtext, rng, odds, cards, ledger, config-schema, mode, hud-queue
    games/{blackjack,poker,slots,roulette,craps,extras}/
    loan/ chaos/ lastchance/ worldgen/ vip/ multiplayer/

```

## 6. Module contract (read this before writing code)

```ts
export interface CasinoModule {
  readonly id: ModuleId;                  // == folder name == lang/<id> == packs/<id>
  readonly config?: readonly ConfigDef[]; // bool | int{min,max,step} | enum{options}
  onStartup?(ctx: StartupContext): void;  // early execution: registerCommand, block/item custom components
  onWorldLoad?(ctx: ModuleContext): void; // subscribe events, intervals, ctx.services.provide(...)
}
```

`ModuleContext` gives you:
- `config`: typed access to your own `<id>.<name>` values, stored as `burmaldaholic:cfg.<id>.<name>`.
- `economy`: `balance`, `change`, `charge`, `pay`, `onChange`.
- `odds`: see "Odds and streaks" below.
- `hud`: `actionbar(player, channel, raw, priority, ttl)` and `title`.
- `services`: the cross-module service locator.
- `log`
- `isCasinoEnabled()`
- `guard(fn)`

The bootstrapper isolates modules: an exception in one module is logged to the Content Log and
does not break the others.

### Ownership rules (keep 12 people from colliding)

1. **Only touch your own folders:**
   - `src/<your path>/`
   - `lang/<id>/`
   - `packs/<id>/BP/**` and `packs/<id>/RP/**`, with files named or foldered by module, for
     example `packs/slots/BP/blocks/slots/slot_machine.json` defining `burmaldaholic:slots_machine`.

   `src/modules.ts`, `modules.json`, `pack.json`, `src/core/**` and `scripts/**` belong to
   core/architect. Your stub is already registered.
2. **Identifiers** are `burmaldaholic:<id>_<name>`: items, blocks, entities, structures, commands (`/burmaldaholic:<id>`),
   dynamic properties (`burmaldaholic:<id>.<key>`), scoreboard objectives (`burmaldaholic_<id>_*`) and tags
   (`burmaldaholic_<id>_*`).
3. **Pure logic lives in `logic/`.** Game math, payouts, hand evaluation and state machines go
   there, with no `@minecraft/*` imports; only relative imports into other `logic/` folders are
   allowed. It is unit-tested with vitest (`*.test.ts` next to the code). Pass an `Rng` in and
   use `seededRng` in tests.
   - Enforced by `check-arch.mjs` and an ESLint rule. The `@minecraft/server` npm package has no
     runtime JS, so a test that pulls it in would fail anyway.
4. **Cross-module calls go through `api.ts` only.**
   - The provider declares an interface and a service name in `<id>/api.ts` and calls
     `ctx.services.provide(...)` in `onWorldLoad`.
   - Consumers call `ctx.services.get<LoanApi>(LOAN_SERVICE)` and handle `undefined`.
   - Importing another module's internals fails `check-arch`. Core is imported only through
     `core/index.ts` or `core/logic/**`.
5. **Shared pack registry files are merged, not owned.** These files are deep-merged by the
   build:
   - `RP/textures/item_texture.json`, `terrain_texture.json`, `flipbook_textures.json`
   - `RP/sounds/sound_definitions.json`, `RP/sounds/music_definitions.json`, `RP/sounds.json`
   - `RP/blocks.json`
   - `BP/item_catalog/crafting_item_catalog.json`

   Put your fragment at the same path under `packs/<id>/`. Header fields such as
   `"resource_pack_name": "burmaldaholic"` and `"texture_name": "atlas.items"` must match
   exactly across modules. Conflicting values, or any other file path provided by two modules,
   fail the build. Never add `manifest.json` under `packs/`.
6. **No hardcoded player-facing text.** See §7.
7. **Respect casino mode.** Wrap handlers with `ctx.guard` and register commands through
   `ctx.registerCommand`.
8. **Odds and streaks.** Games ask `ctx.odds.probability(playerId, '<id>', base)` for binary
   outcomes and call `ctx.odds.recordResult(playerId, 'win'|'loss'|'push')` after every round.
   Chaos, VIP and lastchance adjust odds with `ctx.odds.addModifier(id, fn, order)` and must not
   edit game code. Outcomes with several branches (roulette, slots) scale their weights using
   the returned probability or their own modifier hook documented in their `api.ts`.
9. **Money** goes only through `ctx.economy`:
   - `charge` takes a bet and returns false after telling the player they cannot afford it.
   - `pay` credits winnings.
   - Chip items (`burmaldaholic:chip_*`) and the cashier are core's job (wave 2).

   The balance is stored in the player dynamic property `burmaldaholic:balance` and mirrored to the
   scoreboard `burmaldaholic_balance` (int32, clamped).

## 7. Localization

- **Keys** follow the docs/design scheme `<category>.burmaldaholic.<id>.<...>`, mostly
  `msg.burmaldaholic.<id>.*`, and are owned by the module whose folder they live in. A key that
  names another module's id fails the build. Engine keys that
  contain a `burmaldaholic:` identifier are also allowed, for example `item.burmaldaholic:chip_100`,
  `entity.burmaldaholic:dealer.name` or `tile.burmaldaholic:slots_machine.name`. `pack.name` and
  `pack.description` are core-only.
- **Placeholders must be positional:** `%1$s`, `%2$s`... so the RU text can reorder them. Bare
  `%s` or `%d` fails the build.
- **What the build checks** (it fails, and `npm run check:lang` shows the same errors):
  - key sets differ between `en_US` and `ru_RU`
  - placeholder index sets differ
  - a key is duplicated or defined by two modules
  - a key sits outside its module's namespace
  - a value is empty
  - a plural set is incomplete
  - a `lang/<dir>` does not match any module
- **Code:**
  - `t(key, ...args)` translates. Args can be strings or numbers (shown literally) or nested
    `Raw` values.
  - `plural(base, n, ...extra)` handles counts; `n` becomes `%1$s`.
  - `join(...)` concatenates.
  - `lit()` is only for numbers, player names and `§` codes.
- **`npm run lint` → `check-strings.mjs` fails on:**
  - string or template literals passed to `sendMessage`, `setActionBar`, `setTitle`,
    `updateSubtitle`, or the form methods `title`, `body`, `button`, `label`, `header`,
    `toggle`, `slider`, `dropdown`, `textField`, `submitButton`
  - literal `CustomForm` or `MessageBox` titles
  - `nameTag = '...'`
  - `{text: '<letters>'}` and `lit('<letters>')`
  - static `t('...')` or `plural('...')` keys that are missing from the lang files

  Escape hatch: `// i18n-ignore` on that line, which reviewers will question. Custom command
  `description` strings are exempt because the engine cannot translate them.

### Plurals without knowing the client language

The server cannot know which language a client uses, since rawtext is translated on the client.
So `plural()` picks a **key suffix from the number alone**. The suffixes are the finest split of
the numbers that EN and RU both need:

| suffix | numbers | EN | RU |
|---|---|---|---|
| `.p1` | exactly 1 | singular (`1 chip`) | one (`1 фишка`) |
| `.p21` | ends in 1, not 11, and not 1 itself (21, 31, 101…) | plural (`21 chips`) | one (`21 фишка`) |
| `.p2` | ends in 2–4, not 12–14 (2, 3, 22…) | plural | few (`2 фишки`) |
| `.p5` | everything else (0, 5–20, 25…, 111) | plural | many (`5 фишек`) |

- Every plural key defines all four suffixes in both languages, and the build enforces it.
  English simply repeats its plural form three times.
- Numbers are rounded toward zero and negatives use their absolute value.
- Tests: `src/core/logic/plural.test.ts` (1, 2, 5, 11, 21, 111, 0, 12, 22, 101, 1001, -1).
- Adding a language with other rules means refining this split in one place (`pluralSuffix`).

## 8. UI and HUD guidance

- **Menus and dealers:** `ActionFormData`. **Bets:** `ModalFormData` slider or dropdown.
  **Confirmations:** `MessageFormData`. **Animated reels or wheels:** `CustomForm` with
  `ObservableUIRawMessage`, updated from `system.runInterval`.
- In `ModalFormData`, use **only interactive controls** if you read back `formValues` by index.
  Labels, headers and dividers may take slots in the array.
- **Actionbar:** it is shared by every module, so always go through
  `ctx.hud.actionbar(player, '<id>.<channel>', raw, HudPriority.game)`. The HUD service keeps the
  highest-priority live message on screen and refreshes it every second. Priorities:
  `ambient` < `game` < `alert` (chaos events) < `critical` (debt collectors).
- **Titles:** `ctx.hud.title(player, t(...), t(...))` for big wins and chaos announcements.

## 9. Entities (dealer, loan shark, debt collectors)

- **Custom entities** are defined as `packs/<id>/BP/entities/<id>/*.json` plus
  `packs/<id>/RP/entity/<id>/*.json`.
- To avoid modelling, reuse vanilla geometry and textures in the client entity, for example
  `geometry.villager.v2`, the wandering trader, or `geometry.evoker` / `geometry.vindicator` for
  collectors. Custom skins can come later.
- **Dealer / loan shark:**
  - Components: `minecraft:physics`, `minecraft:pushable` off, `minecraft:persistent`, a
    `minecraft:damage_sensor` that ignores all damage, `minecraft:behavior.look_at_player`.
  - Interaction: `world.afterEvents.playerInteractWithEntity` with a check on
    `target.typeId === 'burmaldaholic:dealer'`, which then opens a form.
  - Name: shown through the translated `entity.burmaldaholic:dealer.name` key. Do not use `nameTag`,
    which cannot be translated.
  - Avoid `minecraft:npc`, whose dialog editing is only for operators.
- **Debt collectors:**
  - A hostile entity whose `minecraft:behavior.nearest_attackable_target` filters on
    `{ "test": "has_tag", "value": "burmaldaholic_loan_debtor" }`.
  - The loan module adds or removes the tag in script and spawns collectors with
    `dimension.spawnEntity` near the debtor. Despawning is done in script once the debt is paid.

## 10. Worldgen (casino buildings)

- **Primary:** data-driven **jigsaw structures**.
  - Files: `BP/worldgen/structures`, `template_pools`, `processors` and `structure_sets`, plus
    `.mcstructure` templates in `BP/structures/worldgen/`.
  - They have needed no experiment since **Bedrock 1.21.120** (Minecraft Wiki history), so they
    work without toggles in 1.26.x.
  - Placement: structure sets with spacing and separation, biome filters, and `/locate` support.
- **Fallback 1:** feature rules plus a `minecraft:structure_template_feature` that places a
  single `.mcstructure`. This has been stable for years, but the size is limited and there is no
  jigsaw.
- **Fallback 2, script:** keep a grid of candidate cells. When a player comes near an unvisited
  cell with loaded chunks, call `world.structureManager.place(...)` and record the cell in a
  world dynamic property. This is fully stable but runs in real time.
- **Loot and NPCs inside structures:** spawn entities in script on first discovery, detected by
  proximity plus the recorded cell, because jigsaw pieces cannot run scripts.

## 11. Commands

```bash
cd bedrock
npm ci                 # install (package-lock.json is committed)
npm run build          # lang check -> esbuild bundle -> build/BP, build/RP -> dist/Burmaldaholic.mcaddon
npm run build:dev      # sourcemaps, no minify, no zip (for deploy)
npm test               # vitest on src/**/*.test.ts (pure logic only)
npm run lint           # tsc --noEmit (stable 2.8.0 typings) + eslint + check-arch + check-strings
npm run check:lang     # lang validation only
npm run deploy         # copy build/{BP,RP} into com.mojang development_*_packs (set MC_COM_MOJANG)
MOD_VERSION=1.2.3 npm run build   # release version override (CI)
```

- Toolchain: Node ≥ 22.12, TypeScript 6.0, esbuild, vitest 5, ESLint 10 with typescript-eslint.
- TypeScript 7 (the native port) is not yet supported by typescript-eslint.
- esbuild bundles to ESM with target `es2023`. `@minecraft/server*` stays external.
- The Bedrock runtime has no `setTimeout` or DOM; use `system.run*`.

## 12. Manual testing (sideload)

- **Quickest, any platform:** open `dist/Burmaldaholic.mcaddon`. Double-click it on Windows, or
  use share/open-with on mobile, and Minecraft imports both packs. Then:
  1. Create a world.
  2. Under Behavior Packs, activate Burmaldaholic. The RP comes along through the dependency.
  3. Check the pack's gear button for the "Casino mode" setting.
  4. Create the world.
- **Faster iteration on Windows:**
  1. Run `npm run build:dev && npm run deploy`. Packs land in `development_behavior_packs` and
     `development_resource_packs`.
  2. Inside the world, run `/reload` to reload scripts after rebuilding. JSON changes need the
     world to be re-entered.
  3. The Windows GDK build (1.21.120+) keeps data in
     `%APPDATA%\Minecraft Bedrock\Users\Shared\games\com.mojang`.
- **Dedicated server (BDS 1.26.30+):**
  1. Copy the packs into `behavior_packs/` and `resource_packs/`.
  2. Add them to `worlds/<world>/world_behavior_packs.json` and `world_resource_packs.json`
     (`[{ "pack_id": "<uuid>", "version": [x, y, z] }]`).
  3. Set `texturepack-required=true` in `server.properties`.
- **Debugging:**
  - Turn on Settings → Creator → Content Log GUI to see script errors and JSON errors.
  - The Minecraft Bedrock Debugger VS Code extension works with `build:dev` sourcemaps; run
    `/script debugger connect`.
- **Smoke checklist:**
  - The pack icon and name are translated.
  - `/burmaldaholic:balance` shows a plural-correct count in EN and RU. Switch the game language and try
    1, 2, 5 and 21.
  - `/burmaldaholic:casino` as op: turning casino mode off makes `/burmaldaholic:balance` reply "casino mode is
    off".
  - The sidebar balance is visible.

## 13. Open risks / verify in game

1. **BP pack settings UI in 1.26.30–1.26.50.** The API is stable, but Microsoft's docs still say
   experimental. If it is hidden, the mode defaults to on and the admin form still works. If v3
   causes trouble, set `pack.json` `manifestFormat` to 2.
2. **Jigsaw JSON `format_version` ≤ 1.26.30.** Community examples use `1.26.50`. Check the
   Content Log.
3. **Custom command descriptions** are not localizable. Admin and player commands are secondary
   to forms and NPCs anyway.
4. **Actionbar** is a single shared line. Use the HUD service, never raw `setActionBar`.
